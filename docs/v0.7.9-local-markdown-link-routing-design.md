# v0.7.9 本地 Markdown 链接复用技术设计

## 背景

当前只要用户在文档中点击本地 Markdown 链接，MarkHola 最终会尝试把目标路径交给
`UserEvent::OpenPath`。工作区本身已经支持“同一路径已打开则激活现有文档”，但 WebView
点击链路没有把“本地 Markdown 链接”作为一个显式能力定义出来，也没有把这条能力纳入
`v0.7.9` 的用户验证入口。

这导致两个问题：

- 用户无法从产品说明中确认“点击本地 Markdown 链接会复用已打开 tab”是受支持能力。
- 链接处理的职责分散在 DOM 点击、WebView 导航拦截和工作区打开逻辑之间，后续改动时不容易
  明确回归边界。

## 目标

- 当链接目标是本地 Markdown 文件时，先判断该文件是否已经在当前工作区中打开。
- 若目标文件已打开，则直接切换到对应 tab，不创建重复 tab。
- 若目标文件未打开，则打开该文件并切换到新 tab。
- 保持当前窗口内完成，不引入新窗口或原生 macOS window tab。
- 保持现有页内锚点 `#heading` 行为不变。
- 保持 `http://`、`https://` 外链行为不变。

## 非目标

- 不改变普通图片、PDF、HTML 或其他非 Markdown 本地文件链接的行为。
- 不在本版本追加“跨文件 hash 锚点滚动定位”。
- 不新增链接悬停提示、右键菜单或最近访问记录。
- 不修改工作区已有的去重规则、Tab 排序规则或关闭逻辑。

## 当前实现分析

现有只读文档点击逻辑位于 `src/implementation/app/shell_script.js`：

- `#...` 页内锚点会被前端直接拦截并滚动到当前文档目标位置。
- `http://`、`https://` 会通过 IPC 发送为 `open-external`。
- 其他链接没有在点击层显式建模，依赖 WebView 后续导航处理。

现有原生导航拦截位于 `src/implementation/app/bootstrap.rs`：

- 当 WebView 尝试导航到 `file://*.md` 或 `file://*.markdown` 时，会阻止导航并转成
  `UserEvent::OpenPath`。

现有工作区打开逻辑位于 `src/implementation/app/document_actions.rs` 与
`src/implementation/workspace.rs`：

- `open_document(...)` 在真正读取文件前会调用 `workspace.find_by_path(path)`。
- 如果路径已打开，则切换活动文档并同步 workspace 状态。
- 如果路径未打开，则读取文件并创建新 tab。

因此，核心产品能力其实已经部分存在，但它当前主要依赖“导航被阻止后再转发”这条隐式链路。
`v0.7.9` 这次需要把本地 Markdown 链接点击变成一条明确、可测试、可说明的产品能力。

## 方案

### 1. 在 WebView 点击层显式识别本地 Markdown 链接

在 `shell_script.js` 的文档点击事件中，继续保留现有顺序：

1. 先处理 tab 点击。
2. 再处理页内 `#...` 锚点。
3. 再处理 `http://`、`https://` 外链。
4. 对剩余链接，基于 `documentBase` 和当前 `href` 解析绝对 URL。

若解析结果为本地 `file:` URL，且路径后缀为 `.md` 或 `.markdown`，则在前端直接
`preventDefault()`，并通过新的 IPC 消息把目标路径交给 Rust 侧。

这样做的原因：

- 产品行为更明确，不再依赖 WKWebView 先尝试导航、再由导航回调阻止。
- 点击时即可明确区分“本地 Markdown 链接”和“其他链接”。
- 更容易补充前端单点测试与日志。

### 2. 新增显式 IPC / UserEvent 路径

新增一条专门用于“本地 Markdown 链接点击”的事件，例如：

- IPC kind：`open-markdown-link`
- Rust 事件：继续复用 `UserEvent::OpenPath`

这里不新建独立业务事件类型，避免和现有 `OpenPath` 分叉。前端只负责把目标路径标准化后
交给现有打开链路，去重与激活仍以 `open_document(...)` 为唯一入口。

### 3. 保留现有工作区去重为唯一真相

不在前端维护“哪些文件已打开”。是否复用现有 tab，仍由 Rust 工作区判断：

- `workspace.find_by_path(path)` 命中时激活现有 tab。
- 未命中时读取并打开目标文件。

这样可以继续复用现有 canonical path 去重逻辑，避免前后端各自维护一套路径状态。

### 4. 保留导航处理作为兜底

`bootstrap.rs` 中现有 `with_navigation_handler` 对本地 Markdown `file://` 的阻止与转发
仍然保留，作为兜底路径。

理由：

- 即使某些链接不是通过前端 click 事件触发，例如浏览器级导航、脚本触发或未来其它入口，
  仍能落回统一的 `OpenPath` 逻辑。
- 这样本次新增是“前端显式建模 + 原生导航兜底”，不是破坏性替换。

## 示例方向

继续复用 `examples/workspace-visual.md`，新增一个“Local markdown links”小节，至少包含：

- 指向 `examples/languages.md` 的本地 Markdown 链接，用于验证“目标已打开时复用现有 tab”
- 指向 `examples/mermaid.md` 的本地 Markdown 链接，用于验证“目标未打开时新开 tab”

不新增额外示例文件，避免把验证入口分散到多个文档。

## 测试影响

需要补三类验证：

1. 前端源码级验证
   - 继续保留锚点与外链分支
   - 新增本地 Markdown 链接识别和 IPC 分支
2. Rust 自动化验证
   - 继续验证同路径重新打开只激活现有文档
   - 验证新增加的状态或消息没有绕开现有去重入口
3. 真实 UI 验证
   - 打开 `workspace-visual.md`
   - 手动同时验证“已打开目标复用 tab”和“未打开目标新开 tab”

## 风险

如果前端只基于原始 `href` 判断，`./foo.md`、`../foo.md`、URL 编码路径或带 query 的本地
链接可能识别不完整，因此必须用 `documentBase` 解析绝对 URL 后再判断协议和扩展名。

如果把“已打开判断”放到前端做，会造成路径规范化不一致，因此本设计明确要求仍由 Rust
工作区负责最终判定。

如果完全移除导航层兜底，可能让非点击触发的本地 Markdown 导航退化，所以本次只新增显式
点击分支，不删现有导航拦截。
